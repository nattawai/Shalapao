### 1 · ยกเลิกการตรวจยอด (unreconcile) — ช่องที่ไม่มีทางถอย

ปิดงวดผิดวัน กรอกยอดผิดแล้วไม่รู้ตัว หรือเผลอกด → **ไม่มีปุ่มถอย** ทางเดียวคือแก้ด้วย SQL

**เหตุผลว่าทำไมเส้นปิดงวดยังควรมีอยู่:** งานจริงของมันไม่ใช่การกันนับซ้ำ (นั่นเป็นผลพลอยได้) แต่คือ**ทำให้ตัวเลขในอดีตไม่เปลี่ยน** — ถ้าไม่มี พอถึง v1 ที่มีสรุปรายเดือน รายงานเดือนสิงหาที่ดูวันนี้จะไม่ตรงกับที่ดูเมื่อเดือนที่แล้ว แล้วไม่มีใครรู้ว่าอันไหนถูก

**เหตุผลที่ต้องมีปุ่มถอย:** เส้นที่ถอยไม่ได้คือกำแพง · เส้นที่ถอยได้แต่ต้องตั้งใจถอยคือลูกบิดประตู — **เราไม่ได้อยากห้ามแก้ เราอยากให้รู้ตัวว่ากำลังแก้สิ่งที่ยืนยันไปแล้ว**

**เหตุผลที่ไม่ใช้แค่คำเตือนแทนเส้น:** คำเตือนกดผ่านจนชิน แล้วอดีตก็ยังเปลี่ยนได้อยู่ดี

🔵 **มี spec เต็มแล้วที่ [`docs/specs/unreconcile.md`](specs/unreconcile.md)** `2026-09-25`

⚠️ **แผนที่เขียนไว้ตอนแรกในหัวข้อนี้ผิด** — เคยเขียนว่า "ถอย `last_reconciled_at` กลับไปค่าก่อนหน้า" แต่ **ไม่มีค่าก่อนหน้าให้ถอย** `pocket.last_reconciled_at` เป็นคอลัมน์เดียวที่ถูกเขียนทับทุกครั้ง ระบบไม่เก็บประวัติการตรวจยอดเลย

```
เคาะแล้ว 2026-09-25 → เพิ่มตาราง pocket_reconcile จดทุกครั้งที่ตรวจยอด
  → ถอย last_reconciled_at กลับไปค่าใน previous_line ของแถวล่าสุด
  → soft delete รายการปรับที่สร้างตอนนั้น (ถ้ามี — ส่วนต่าง 0 ไม่สร้าง)
  → ประทับ cancelled_at ที่แถวนั้น
  → ทั้งหมดใน db.batch เดียว
  → 🔴 ต้องมี ancestor guard: แม่ปิดคลุมอยู่ ยกเลิกลูกไม่ได้
```

**ของแถมที่ได้ฟรีจากตารางนี้:** ข้อ 4 ข้างล่าง (แสดง "ตรวจยอดล่าสุด" บนหน้าแรก) ใช้ข้อมูลชุดเดียวกัน ไม่ต้องแก้ schema สองรอบ

**ทางเลือกถ้าใช้ไปแล้วรู้สึกว่าเส้นเกะกะกว่าช่วย:** เอาเส้นออกแล้วใช้คำเตือนแทน — แต่จะเสียความนิ่งของตัวเลขในอดีต และถ้ากลับมาใส่เส้นตอนมีข้อมูลเยอะแล้วจะแพงกว่ามาก

### 2 · เปลี่ยนคำทั้งหมดให้เป็นภาษาคน

**"ปิดงวด" กับ "กระทบยอด" เป็นศัพท์บัญชี ไม่ใช่ความคิดของผู้ใช้** — คนทั่วไปคิดว่า *"เงินในแอปตรงกับธนาคารหรือยัง"*

| ตอนนี้ | ควรเป็น |
|---|---|
| วันปิดงวด | ตรวจยอดถึงวันที่ |
| ยืนยันปิดงวด | ยืนยันว่ายอดตรง / ยืนยันตามธนาคาร |
| กระทบยอด | ตรวจยอดกับธนาคาร |
| งวดที่กระทบยอดแล้ว | ช่วงที่ตรวจไปแล้ว |

**🔴 กับดักของคำว่า "ยืนยันว่ายอดตรง":** ใช้ได้เฉพาะตอนส่วนต่าง = 0 · ถ้ามีส่วนต่าง ผู้ใช้ไม่ได้ยืนยันว่าตรง แต่กำลัง **"เชื่อธนาคารแล้วแก้ให้ตรง"**
→ เปลี่ยนคำบนปุ่มตามสถานการณ์ และ**ใส่ตัวเลขลงบนปุ่ม**

```
ส่วนต่าง 0        [ ยืนยันว่ายอดตรง ]
ส่วนต่าง −300     [ บันทึกส่วนต่าง −300 แล้วยืนยัน ]
```

**เหตุผล:** ในจังหวะที่ระบบกำลังจะเขียนรายการเงินให้ ผู้ใช้ควรเห็นว่าจะเขียนเท่าไรก่อนกด ไม่ใช่เห็นหลังกด

### 3 · ข้อความตอนโดนบล็อก ต้องสอนและให้ทางออกพร้อมกัน

```

✅ วันที่ 20 ก.ย. อยู่ในช่วงที่คุณตรวจยอดกับธนาคารไปแล้วเมื่อ 23 ก.ย.
   ถ้าเพิ่มรายการย้อนหลัง ยอดจะไม่ตรงกับธนาคารอีก
   [ เพิ่มเป็นรายการของวันนี้แทน ]   [ ยกเลิกการตรวจยอดครั้งนั้น ]

### 4 · แสดง "ตรวจยอดล่าสุด" บนหน้าแรก

```

**เหตุผล:** ให้ฟีเจอร์สอนตัวเองผ่านผลลัพธ์ · **แสดงผลของแนวคิด ดีกว่าแสดงชื่อของแนวคิด** — ผู้ใช้เห็นทุกวันโดยไม่ต้องอ่านอะไร แล้วเข้าใจเองว่าระบบจำได้ว่าตรวจถึงไหน

พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 ให้สิทธิ์สามข้อนี้กับเจ้าของข้อมูล — **ไม่ใช่สิ่งที่เราเลือกให้หรือไม่ให้** · ตอนนี้เขียนในเอกสารว่า "ติดต่อทางอีเมลแล้วเจ้าของทำให้ด้วยมือ" ซึ่งรับได้ตอนใช้คนเดียว แต่ผลักภาระให้ผู้ใช้เมื่อเปิดจริง

**เหตุผลที่ต้องทำก่อน `1.0.0` ไม่ใช่หลัง:** วันที่มีผู้ใช้คนที่สองแล้วเขาขอลบข้อมูล เราต้องทำได้ภายใน 30 วันตามที่เอกสารสัญญาไว้ · ถ้าทำด้วย SQL มือทุกครั้ง จะพลาดแน่นอนเมื่อมีคนขอพร้อมกันหลายคน

### ลบบัญชีและข้อมูลทั้งหมดของตัวเอง
ไม่มี endpoint เลย · ตอนนี้ต้องลบด้วย `wrangler d1 execute` เอง
ต้องลบข้าม 4 ตาราง (`entry` · `pocket_member` · `pocket` · `app_user`) ในลำดับที่ไม่ทำให้ FK พัง — **ทำมือแล้วลืมตารางเดียวจะเหลือแถวกำพร้า**
หมายเหตุ: ต้องบอกผู้ใช้ด้วยว่าระบบย้อนเวลา 30 วันของ D1 ยังเก็บประวัติไว้ ลบแล้วไม่หายทันทีทั้งหมด

### ดาวน์โหลดข้อมูลของตัวเอง
ไม่มีทาง export เลย · PDPA ให้สิทธิ์ทั้งการขอสำเนาและการขอให้โอนไปผู้ควบคุมรายอื่น
รูปแบบที่พอ: JSON หรือ CSV ของกระเป๋า + รายการทั้งหมด

### แก้ข้อมูลที่ไม่ถูกต้อง
แก้รายการได้บางส่วน (ลบแล้วสร้างใหม่) แต่ **แก้ชื่อกระเป๋าไม่ได้เลย** — ดูข้อถัดไป

## 🔵 มาจากการใช้จริง — น้ำหนักสูงสุด

### แก้ชื่อกระเป๋าไม่ได้เลย
`2026-09-25` · เจอตอนไล่ดูว่าอะไรที่ระบบยังทำไม่ได้

ทั้งระบบมีคำสั่งแก้ไขอยู่ตัวเดียวคือ `DELETE /api/entries/:id` — **ไม่มี `PATCH` หรือ `PUT` สักตัว**

พิมพ์ชื่อกระเป๋าผิดตอนสร้าง → แก้ไม่ได้ ลบก็ไม่ได้ → ทนดูชื่อผิดตลอดไป

**เหตุผลที่เจ็บกว่าเรื่องลบกระเป๋า:** การลบมีทางอ้อม (สร้างใบใหม่แล้วไม่ใช้ใบเก่า) แต่ชื่อผิดอยู่บนหน้าแรกให้เห็นทุกครั้งที่เปิดแอป
**เหตุผลที่เร่งกว่าที่คิด:** เป็นสิทธิ์ตาม PDPA ข้อ "ขอแก้ไขข้อมูลที่ไม่ถูกต้อง" ด้วย ไม่ใช่แค่ความสะดวก

`PATCH` ตัวแรกจะเป็นตัวกำหนดรูปแบบของทุกตัวถัดไป — ควรคิดตอนออกแบบว่าอะไรแก้ได้บ้าง (ชื่อ · `sort_order` · `category_id`) และอะไรห้ามแก้ (`kind` เป็น enum ระบบ · `parent_id` มีกฎของตัวเองอยู่แล้ว)

### แก้รายการที่ลงไปแล้วไม่ได้
`2026-09-25`

แก้บันทึก · แก้ยอด · แก้วันที่ · ย้ายกระเป๋า — ทำไม่ได้ทั้งหมด ต้องลบแล้วสร้างใหม่

**เหตุผลที่ยังไม่เร่ง:** มีทางอ้อมที่ใช้งานได้ (ลบ + สร้างใหม่) เสียแค่สองจังหวะ
**แต่แยกออกเป็นสองกลุ่มตอนออกแบบ:**

```
กลุ่ม        ฟิลด์                  วิธีแก้                      ในช่วงที่ตรวจยอดแล้ว
──────────────────────────────────────────────────────────────────────────
ป้าย        บันทึก · หมวด           UPDATE ได้ตรง ๆ              ✅ แก้ได้
เงิน        ยอด · วันที่ · กระเป๋า     soft delete + create ใหม่    ❌ บล็อก
```

🔴 **"แก้เงิน" ห้ามเป็น `UPDATE` ไม่ว่ากรณีใด แม้ในงวดที่ยังเปิดอยู่**

`entry.repository` **ต้องไม่มีฟังก์ชันที่แก้ `amount_satang` `occurred_on` หรือ `pocket_id` ของแถวเดิมเลย** — ถ้ามี วันหนึ่งจะมีคนเรียกมันข้ามเส้นตรวจยอด แล้วยอดที่ยืนยันไปแล้วจะเปลี่ยนเงียบ ๆ โดยไม่มีร่องรอย

```
"แก้ยอด" ที่ถูกต้อง = soft delete แถวเดิม + create แถวใหม่ ใน db.batch เดียว
                      ทั้งสองแถวต้องผ่าน assertNotReconciled ทั้งคู่
                      (แถวเดิมด้วย occurred_on เดิม · แถวใหม่ด้วย occurred_on ใหม่)
```

**เหตุผลที่ต้องเช็คสองวัน:** ย้ายรายการจาก 20 ก.ย. มาเป็น 26 ก.ย. — วันใหม่ผ่าน แต่การลบของวันที่ 20 ทำให้ยอดที่ตรวจไปแล้วเปลี่ยน

**เหตุผลที่ป้ายแก้ได้แม้ในงวดเก่า:** การติดหมวดย้อนหลัง (สำหรับ dashboard) ไม่แตะตัวเลขเลย ถ้าห้ามด้วยจะจัดหมวดข้อมูลเก่าไม่ได้ตลอดกาล



### หน้ากระเป๋าแม่ต้องแสดงรายการของทั้งกิ่ง
`2026-09-24`

ตอนนี้กดเข้ากระเป๋าแม่แล้วเห็นเฉพาะรายการของใบนั้นเอง

**เหตุผล:** หน้าแรกแสดงยอดแม่เป็น rollup (รวมลูก) แต่หน้ารายการอธิบายได้แค่ส่วนเดียว — **ตัวเลขที่แสดงกับรายการที่อธิบายมันไม่ใช่ชุดเดียวกัน** นี่เป็นความไม่สอดคล้องเชิงตรรกะ ไม่ใช่แค่ฟีเจอร์ที่ขาด

**รูปแบบที่เลือก:** เรียงตามเวลา + ป้ายชื่อกระเป๋าต่อแถว (ไม่ใช่จัดกลุ่มตามกระเป๋า)

```
2026-09-24                    +2,000.00
remark                        [กระเป๋า B]
2026-09-24                    +3,000.00
remark                        [กระเป๋า B1]
```

**เหตุผลที่ไม่จัดกลุ่ม:** หน้านี้มีไว้เทียบกับ statement ธนาคารซึ่งเรียงตามเวลาเสมอ · ถ้าจัดกลุ่มตามกระเป๋า ลำดับเวลาจะแตกเป็นหลายท่อน แล้วไล่เทียบทีละบรรทัดไม่ได้ · และแบบจัดกลุ่มก็คือเอาหลายหน้ามาต่อกัน ซึ่งกดเข้าดูทีละใบได้อยู่แล้ว

ป้ายแสดงเฉพาะตอนเปิดกระเป๋าที่มีลูก · ตัวเลือกเสริม: สวิตช์ `[รวมลูก] เฉพาะใบนี้` ดีฟอลต์รวมลูก
**ต้นทุนต่ำ:** ใช้ view `pocket_subtree` ที่มีอยู่แล้ว · เพิ่ม `pocketName` ในคำตอบ

### ย่อ/กางกระเป๋าลูกได้
`2026-09-24`

**เหตุผล:** ถ้ามีลูกหลายใบ รายการจะยาวจนเลื่อนหาลำบาก · **ย่อแล้วไม่เสียข้อมูล** เพราะยอดแม่เป็น rollup อยู่แล้ว — เห็นยอดรวมโดยไม่ต้องเห็นรายละเอียด

จำสถานะย่อ/กางใน `localStorage` ได้ — **นี่คือค่าตั้งหน้าจอ ไม่ใช่ข้อมูลเงิน** จำผิดก็แค่กดใหม่ ไม่มีใครเสียหาย

### แสดงวันที่อัปเดตล่าสุดของแต่ละกระเป๋า
`2026-09-24`

**ใช้ `occurred_on` ล่าสุด ไม่ใช่ `created_at`**

**เหตุผล:** ถ้าวันนี้ย้อนกรอกข้อมูลเดือนสิงหา `created_at` จะขึ้น "วันนี้" ทั้งที่กระเป๋านั้นไม่มีข้อมูลอะไรหลัง 15 ส.ค. เลย — บอกว่าอัปเดตแล้วทั้งที่ยังไม่ทันความจริง · `occurred_on` ตอบคำถามที่ถามจริงว่า **"กระเป๋านี้รู้เรื่องโลกถึงวันไหน"**

กระเป๋าแม่ใช้วันล่าสุดของทั้งกิ่ง (สอดคล้องกับยอดที่เป็น rollup) · ใบที่ยังไม่มีรายการขึ้น "ยังไม่มีรายการ"

### ย้ายกระเป๋าไปอยู่ใต้กระเป๋าอื่น
`2026-09-24`

**วิธี: เปลี่ยน `parentId` เท่านั้น ห้ามลบแล้วสร้างใหม่**

**เหตุผล:** `entry.pocket_id` ผูกกับ `id` เดิม · ลบแล้วสร้างใหม่ = ได้ `id` ใหม่ = รายการทั้งหมดกลายเป็นกำพร้า ประวัติหายทั้งก้อน · การย้ายคือการเปลี่ยน**โครงสร้าง** ไม่ใช่การเปลี่ยน**เงิน** — เงินไม่ได้ไปไหน แค่ถูกนับรวมในกิ่งอื่น

**กฎ 1 · ห้ามย้ายเข้าไปในลูกของตัวเอง**
schema มี `CHECK (parent_id <> id)` กันแค่ชั้นเดียว ไม่ได้กันวงที่ลึกกว่า · ถ้าเกิดวง recursive CTE จะเดินไม่จบ query ค้างถาวร · ใช้ view `pocket_subtree` เช็คว่าแม่ใหม่ไม่อยู่ใน subtree ของตัวที่จะย้าย

**กฎ 2 · 🔴 ห้ามย้ายถ้าทำให้ยอดที่กระทบแล้วเปลี่ยน**
ย้ายกระเป๋าที่มีเงินออกจากแม่เดิม = rollup ของแม่เดิมลดลง **ทุกวันย้อนหลังไปตลอด** · ถ้าแม่เดิมเคยกระทบยอดแล้วตรงกับธนาคาร ตอนนี้จะไม่ตรงโดยไม่มีอะไรบอก — บั๊กชนิดเดียวกับการลงรายการย้อนหลัง แค่มาจากคนละทาง
→ ถ้ากิ่งที่จะย้ายมีรายการลงวันก่อนหรือเท่ากับเส้นกระทบยอดของสายแม่เดิมหรือสายแม่ใหม่ → ปฏิเสธ (409)
**ทางออกถ้าจำเป็น:** โยกเงินออกให้เหลือ 0 → ย้าย → โยกกลับ · เงินเดินผ่านรายการที่มองเห็นได้ ไม่ใช่เปลี่ยนเงียบ ๆ

### แสดงข้อมูลที่เก็บไว้ทันที แล้วโหลดใหม่เบื้องหลัง
`2026-09-24`

**เป้าหมาย: รองรับผู้ใช้ที่เน็ตช้าตอนเปิดให้คนอื่นใช้** ไม่ใช่ความสะดวกของเจ้าของ

```
เน็ตดี   รอ 1 วินาที   →  รำคาญนิดหน่อย
เน็ตช้า  รอ 8 วินาที   →  ปิดทิ้งแล้วไม่กลับมา
```

**ทำ**
1. เก็บคำตอบจากเซิร์ฟเวอร์ใน `localStorage` — **ห้ามเก็บเลขที่ฝั่งหน้าจอคำนวณเอง**
2. เปิดแอป → แสดงของเก่าทันที + ป้าย "ข้อมูลเมื่อ 14:32 · กำลังอัปเดต…" → โหลดใหม่เบื้องหลัง
3. `cache ≤ 3 วัน` แสดงทันที · `> 3 วัน` พยายามโหลดก่อน **ถ้าล้มเหลวให้แสดงของเก่าพร้อมป้ายเตือน ห้ามแสดงหน้าว่าง**
4. ปุ่ม sync ที่หัวหน้าแรก
5. ใส่ timeout ให้ `fetch` ฝั่งหน้าจอ (~10 วินาที) + ปุ่มลองใหม่

**เหตุผลข้อ 1 — ห้ามคำนวณยอดฝั่งหน้าจอ:** ยอดเงินไม่ได้ถูก "เขียน" แต่ถูก "คำนวณ" จาก view · ถ้า cache คำนวณเอง จะมีสูตรคำนวณเงินสองชุด (SQL + JS) แล้ววันหนึ่งจะให้คำตอบไม่ตรงกันโดยไม่มีอะไรบอก — **การมีสูตรคำนวณเงินสองชุดคือหนี้ที่จ่ายคืนแพงที่สุดในระบบบัญชี**

**เหตุผลข้อ 3 — ข้อมูลเก่าดีกว่าไม่มีข้อมูล** ตราบใดที่บอกชัดว่าเก่า · คนเน็ตช้าที่โหลดไม่สำเร็จจะเห็นหน้าว่างเปล่าทั้งที่มีข้อมูลอยู่ในเครื่อง

**เหตุผลข้อ 5:** `AbortSignal` ใส่ไว้แล้วฝั่ง Worker→LINE แต่ฝั่งมือถือ→Worker ยังไม่มี · บนเน็ตแย่ request จะค้างไปเรื่อย ๆ ผู้ใช้ไม่ได้ทั้งข้อมูลและไม่ได้ทั้ง error ซึ่งแย่กว่าทั้งสองอย่าง

**ไม่ทำ · cache version / ETag** — ลดขนาดข้อมูลแต่ไม่ลดจำนวนรอบวิ่งไปกลับ ซึ่ง**รอบคือตัวที่กินเวลาบนเน็ตช้า ไม่ใช่ขนาด** · ค่อยทำตอนรายการเดินบัญชียาวหลายร้อยแถวใน v1 พร้อมกับการแบ่งหน้า

**ไม่ทำ · offline-first** (เขียนได้ตอนไม่มีเน็ต) — ต้องมี IndexedDB + คิวรอส่ง + วิธีตัดสินเมื่อข้อมูลชนกัน · คนละขนาดกับ cache และยังไม่ใช่ปัญหาที่มี

### ยอดกระเป๋าแม่ แสดงยอดของตัวเองในวงเล็บ

**เหตุผล:** ตอนนี้เห็นแต่ยอดรวม ไม่รู้ว่าในนั้นเป็นเงินที่ยังไม่ได้แบ่งเข้าซองลูกเท่าไร — **ซึ่งเป็นตัวเลขที่ต้องรู้ตอนจะแบ่งเงิน** ว่าเหลือให้แบ่งอีกเท่าไร

**เคาะแล้ว `2026-09-30` → สองบรรทัด ยอดรวมใหญ่ ยอดตัวเองเล็ก · ใช้คำว่า "คงเหลือ"**

```
Base Make

คงเหลือ 2,000.00        ← ยอดของตัวเอง (ตัวเล็ก)
```

**เหตุผลที่เลือก "คงเหลือ":** เป็นคำมาตรฐานที่ธนาคารไทยใช้ — คนไทยเห็นแล้วไม่ต้องแปล
คำที่ถูกต้องกว่าทางความหมาย (`ยังไม่ได้แบ่ง` · `ในกระเป๋านี้เอง`) เป็นคำที่ไม่มีที่ไหนใช้ **ความคุ้นเคยมีค่าจริง**

⚠️ **AI ผู้ช่วยไม่เห็นด้วย — จดคำทำนายไว้ให้ตรวจสอบ `2026-09-30`**

```
คำทำนาย   คนที่ไม่เคยใช้แอปจะอ่าน "20,000 / คงเหลือ 2,000"
          ว่า "มี 20,000 ใช้ไป 18,000 เหลือ 2,000"
เหตุผล     ทุกตัวเลขในแอปนี้เป็น "คงเหลือ" อยู่แล้ว ตัวใหญ่ก็ใช่ ตัวเล็กก็ใช่
          พอใช้คำเดียวกัน สมองจึงเดาว่าตัวเล็กคือ "ที่เหลือหลังหักตัวใหญ่"
          — ตีความเป็นเรื่องเวลา (ก่อน/หลัง) แทนที่จะเป็นเรื่องสถานที่ (แม่/ลูก)
```

**สิ่งที่จะชี้ขาด:** ตอนทดสอบคำกับคนที่ไม่รู้เรื่อง เปิดหน้าแรกให้ดูแล้วถาม *"2,000 นี้คือเงินอะไร"*

```
ตอบว่า "เงินที่ยังไม่ได้เอาไปแบ่ง"   →  ไวถูก · ปิดเรื่องนี้ ลบย่อหน้านี้ทิ้ง
ตอบว่า "เงินที่เหลือหลังใช้ไป"       →  AI ถูก · กลับมาพิจารณาคำใหม่
```

**ไม่ใช่เรื่องถูกผิด แต่เป็นเรื่องจังหวะ** — ตอนนี้ผู้ใช้มีคนเดียวคือคนที่ออกแบบเอง ไม่มีปัญหาการตีความ · ความเสี่ยงจะมาถึงตอน `1.0.0` ที่มีคนนอกใช้

     [20%] [50%] [100%]

**เหตุผล:** ตอนนี้ต้องจำเองว่ากระเป๋าต้นทางมีเท่าไร **หรือกดกลับไปดูหน้าแรกแล้วกลับมา** และมีโอกาสโยกเกินที่มีจริง

🔵 **ส่วนที่ไวคิดไว้ถูกและสำคัญที่สุด** — เมื่อโยกหลายรายการพร้อมกัน `%` ต้องคิดจากยอดที่เหลือ**หลังหักรายการอื่นในฟอร์มแล้ว** และ **เป็นแค่การคำนวณ ยังไม่โอนจริงจนกว่าจะกดยืนยัน**

**เรื่องที่ต้องระวังตอนทำ**

```
% คิดจากยอดของกระเป๋าเอง ไม่ใช่ rollup — โยกเงินของลูกไม่ได้
กด 100% แล้วเพิ่มแถวใหม่ → แถวใหม่จะได้ 0 ต้องบอกผู้ใช้ให้รู้ ไม่ใช่ปล่อยเงียบ
20% ของ 10,706.67 = 2,141.334 → ต้องปัดเป็นสตางค์จำนวนเต็ม
   ใช้ splitProrata() ที่มีอยู่แล้ว ห้ามปัดเอง
ยอดรวมทุกแถวเกินยอดที่มี → ต้องเตือนตั้งแต่ในฟอร์ม ไม่ใช่ตอนกดยืนยัน
```

### ชื่อกระเป๋าแม่หลุดในข้อความ error ตอน v3
`2026-09-28` · เจอตอนตรวจ PR #45 (unreconcile)

```ts
findLockingAncestor()   // ไม่กรอง pocket_member โดยตั้งใจ — เป็นด่าน integrity
                        // เหมือน assertNotReconciled
→ 409 "ต้องยกเลิกการตรวจยอดของ {ชื่อกระเป๋าแม่} ({วันที่}) ก่อน"
```

```
v0  ไม่มีปัญหา — กระเป๋าทั้งหมดเป็นของคนเดียว
v3  เป็นสมาชิกกระเป๋าลูกแต่ไม่ใช่สมาชิกกระเป๋าแม่
    → ชื่อกระเป๋าแม่ของคนอื่นหลุดออกมาในข้อความ error
```

**เหตุผลที่ยังไม่แก้:** กระเป๋าร่วมอยู่ v3 · แก้ตอนนี้ = เขียนโค้ดกันปัญหาที่ยังเกิดไม่ได้ และจะไม่มี test พิสูจน์ว่าทำงาน (ยังไม่มีสถานการณ์ให้ทดสอบ)

**วิธีแก้ตอน v3:** คืนชื่อเฉพาะเมื่อผู้ใช้เป็นสมาชิกของกระเป๋าแม่ด้วย · ถ้าไม่ใช่ บอกแค่ *"ต้องยกเลิกการตรวจยอดของกระเป๋าแม่ก่อน"* — ผู้ใช้ยังรู้ว่าต้องทำอะไร โดยไม่รู้ว่ากระเป๋านั้นชื่ออะไร

🔴 **ต้องทำพร้อมกับ `left_at` และสิทธิ์ในกระเป๋าร่วม** ไม่ใช่ทำแยก — เป็นการรั่วประเภทเดียวกัน

## บันทึกการตัดสินใจเชิงสถาปัตยกรรม (ยังไม่ทำ แต่ตัดสินแล้ว)

### `category` คืออะไร — เคาะแล้ว
`2026-09-25` · ตอบคำถามว่า category มีไว้ทำอะไร (API มีแล้วแต่ไม่มีหน้าจอ)

**นิยาม:** ป้ายบอกว่า **"ค่าใช้จ่ายรายการนี้เป็นค่าอะไร"** ผู้ใช้สร้างเองได้
**ปลายทาง:** dashboard สรุปว่าเดือนนี้ใช้จ่ายอะไรไปเท่าไร

**🔴 ต้องลบ `pocket.category_id` ทิ้ง เก็บไว้เฉพาะ `entry.category_id`**

ตอนนี้ `category_id` อยู่สองที่คนละความหมาย — บนกระเป๋า ("กระเป๋านี้ไว้ทำอะไร") และบนรายการ ("รายการนี้เป็นค่าอะไร") · สิ่งที่ต้องการคืออันหลัง

**เหตุผลที่อันบนกระเป๋าซ้ำซ้อน:** ชื่อกระเป๋าจริงของไวคือหมวดอยู่แล้ว (Mobile · Subscription · Healing · Easy pass) — ติดป้าย "ค่าโทรศัพท์" ให้กระเป๋าชื่อ "Mobile" ไม่เพิ่มข้อมูลอะไร · ส่วนการจัดกลุ่มกระเป๋าหลายใบ กระเป๋าแม่ทำหน้าที่นี้อยู่แล้ว
**เหตุผลที่ต้องลบ ไม่ใช่ปล่อยไว้เฉย ๆ:** ถ้ามีสองที่ วันหนึ่งจะมีคนสับสนว่าหมวดของรายการควรตามกระเป๋าหรือตามที่กรอก แล้วเขียนตรรกะผสมกันจนแก้ยาก

**dashboard จะมีค่าตรงไหน:** กระเป๋าที่เป็นวัตถุประสงค์เฉพาะตอบตัวเองได้จากยอดอยู่แล้ว — **ตัวที่ต้องการหมวดจริงคือกระเป๋าใช้จ่ายรวม (มือเติบ)** ที่เงินไหลออกหลายเรื่องปนกัน

**🟢 ไม่ต้องรีบ เพราะหมวดเป็นป้าย ไม่ใช่เงิน**
การแก้หมวดไม่ทำให้ยอดเปลี่ยน → **แก้ย้อนหลังได้แม้ในงวดที่ปิดแล้ว** โดยไม่ละเมิดกฎกระทบยอด (กฎนั้นคุ้มครองจำนวนเงินกับวันที่ ไม่ใช่ป้าย)
แต่ยิ่งนานยิ่งมีของค้างให้ติดป้าย และจะจำไม่ได้แล้วว่า "Shopee 871 บาท" คือซื้ออะไร

**ตัดสินตอนออกแบบ:** ห้ามบังคับใส่หมวดทุกรายการ — ถ้าบังคับ การบันทึกจะช้าลงทุกครั้งแล้วจะเลิกกรอก · **dashboard ที่มีข้อมูล 70% ดีกว่า dashboard ที่ไม่มีข้อมูลเลยเพราะคนเลิกใช้**

### D1 backup — ไม่ต้องสร้าง มีให้แล้ว
`2026-09-25` · แก้ความเข้าใจผิดที่เคยจดไว้

D1 มี **Time Travel เปิดอยู่ตลอดโดยอัตโนมัติ** ย้อนกลับได้ทุกนาทีภายใน 30 วัน ไม่มีค่าใช้จ่ายเพิ่มแม้บนแผนฟรี · ไม่ต้องตั้งค่า ไม่ต้อง export เอง

**สิ่งที่ยังควรทำคือ "ซ้อม" ไม่ใช่ "สร้าง"** — ลองกู้คืนสักครั้งตอนยังไม่มีข้อมูลสำคัญ · ตอนของหายจริงไม่ใช่เวลาที่ควรมาอ่านเอกสารครั้งแรก


### Message queue — ยังไม่ต้อง · จะจำเป็นตอน v3
`2026-09-24` · ตอบคำถามว่าคิวช่วยอะไรได้บ้าง

**ตอนนี้ไม่ช่วย** เพราะงานทุกอย่างที่มี ผู้ใช้ต้องการคำตอบทันที — เพิ่มรายการต้องเห็นยอดเปลี่ยนเดี๋ยวนั้น · เช็คยอดต้องเห็นส่วนต่างเดี๋ยวนั้น · **คิวช่วยตอนที่งานเลื่อนได้ ถ้าเลื่อนไม่ได้ก็แค่เพิ่มชิ้นส่วนให้พังโดยไม่ได้อะไร**

**จะจำเป็นตอน v3 — บอทอ่านสลิป**
```
ส่งรูปสลิป → LINE ยิง webhook → LINE รอคำตอบ
             ถ้าเราไปเรียก AI อ่านรูป (หลายวินาที) LINE จะถือว่าไม่ตอบแล้วส่งซ้ำ
             → อ่านสลิปเดียวกันสองรอบ → ลงเงินซ้ำ
ทางที่ถูก    ตอบ LINE ทันทีว่ารับแล้ว → โยนงานอ่านรูปเข้าคิว → ค่อยทำ
```
*(ยังไม่ยืนยันว่า LINE ให้เวลากี่วินาทีและส่งซ้ำกี่ครั้ง — ต้องอ่านเอกสารตอนถึงจริง)*

**v1 อาจต้อง** ถ้าแจ้งเตือนรายเดือนมีผู้ใช้หลายร้อยคน — ยิงรวดเดียวจะชนลิมิตของ LINE คิวช่วยทยอยส่งและลองใหม่

**🔴 ลำดับที่ต้องลองก่อนเสมอ: `ctx.waitUntil()`**
Cloudflare Workers ตอบผู้ใช้ไปก่อนแล้วทำงานต่อหลังส่งคำตอบได้ — ครอบคลุมเคส "งานช้า ผู้ใช้ไม่ต้องรอ" เกือบหมดโดยไม่ต้องเพิ่มโครงสร้างอะไรเลย

คิวจำเป็นเมื่อ `waitUntil` ไม่พอ:
- งานล้มแล้วต้องลองใหม่อัตโนมัติ (`waitUntil` ล้มแล้วหายเลย)
- Worker ตายกลางทางแล้วงานต้องรอด (`waitUntil` ตายตาม)
- ต้องคุมจังหวะไม่ให้ยิงถี่เกินลิมิต (`waitUntil` คุมไม่ได้)
