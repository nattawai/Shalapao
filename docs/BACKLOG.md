ตอนนี้กดเข้ากระเป๋าแม่แล้วเห็นเฉพาะรายการของใบนั้นเอง

**เหตุผล:** หน้าแรกแสดงยอดแม่เป็น rollup (รวมลูก) แต่หน้ารายการอธิบายได้แค่ส่วนเดียว — **ตัวเลขที่แสดงกับรายการที่อธิบายมันไม่ใช่ชุดเดียวกัน** นี่เป็นความไม่สอดคล้องเชิงตรรกะ ไม่ใช่แค่ฟีเจอร์ที่ขาด

**รูปแบบที่เลือก:** เรียงตามเวลา + ป้ายชื่อกระเป๋าต่อแถว (ไม่ใช่จัดกลุ่มตามกระเป๋า)

```
2026-09-24                    +2,000.00
remark                        [กระเป๋า B]
2026-09-24                    +3,000.00
remark                        [กระเป๋า B1]
```

**เหตุผลที่ไม่จัดกลุ่ม:** หน้านี้มีไว้เทียบกับ statement ธนาคารซึ่งเรียงตามเวลาเสมอ · ถ้าจัดกลุ่มตามกระเป๋า ลำดับเวลาจะแตกเป็นหลายท่อน แล้วไล่เทียบทีละบรรทัดไม่ได้ · และแบบจัดกลุ่มก็คือเอาหลายหน้ามาต่อกัน ซึ่งกดเข้าดูทีละใบได้อยู่แล้ว

ป้ายแสดงเฉพาะตอนเปิดกระเป๋าที่มีลูก · ตัวเลือกเสริม: สวิตช์ `[รวมลูก] เฉพาะใบนี้` ดีฟอลต์รวมลูก

### แสดงวันที่อัปเดตล่าสุดของแต่ละกระเป๋า
`2026-09-24`

**ใช้ `occurred_on` ล่าสุด ไม่ใช่ `created_at`**

**เหตุผล:** ถ้าวันนี้ย้อนกรอกข้อมูลเดือนสิงหา `created_at` จะขึ้น "วันนี้" ทั้งที่กระเป๋านั้นไม่มีข้อมูลอะไรหลัง 15 ส.ค. เลย — บอกว่าอัปเดตแล้วทั้งที่ยังไม่ทันความจริง · `occurred_on` ตอบคำถามที่ถามจริงว่า **"กระเป๋านี้รู้เรื่องโลกถึงวันไหน"**

กระเป๋าแม่ใช้วันล่าสุดของทั้งกิ่ง (สอดคล้องกับยอดที่เป็น rollup) · ใบที่ยังไม่มีรายการขึ้น "ยังไม่มีรายการ"

### ย้ายกระเป๋าไปอยู่ใต้กระเป๋าอื่น
`2026-09-24`

**วิธี: เปลี่ยน `parentId` เท่านั้น ห้ามลบแล้วสร้างใหม่**

**เหตุผล:** `entry.pocket_id` ผูกกับ `id` เดิม · ลบแล้วสร้างใหม่ = ได้ `id` ใหม่ = รายการทั้งหมดกลายเป็นกำพร้า ประวัติหายทั้งก้อน · การย้ายคือการเปลี่ยน**โครงสร้าง** ไม่ใช่การเปลี่ยน**เงิน** — เงินไม่ได้ไปไหน แค่ถูกนับรวมในกิ่งอื่น

**กฎ 1 · ห้ามย้ายเข้าไปในลูกของตัวเอง**
schema มี `CHECK (parent_id <> id)` กันแค่ชั้นเดียว ไม่ได้กันวงที่ลึกกว่า · ถ้าเกิดวง recursive CTE จะเดินไม่จบ query ค้างถาวร · ใช้ view `pocket_subtree` เช็คว่าแม่ใหม่ไม่อยู่ใน subtree ของตัวที่จะย้าย

**กฎ 2 · 🔴 ห้ามย้ายถ้าทำให้ยอดที่กระทบแล้วเปลี่ยน**
ย้ายกระเป๋าที่มีเงินออกจากแม่เดิม = rollup ของแม่เดิมลดลง **ทุกวันย้อนหลังไปตลอด** · ถ้าแม่เดิมเคยกระทบยอดแล้วตรงกับธนาคาร ตอนนี้จะไม่ตรงโดยไม่มีอะไรบอก — บั๊กชนิดเดียวกับการลงรายการย้อนหลัง แค่มาจากคนละทาง
→ ถ้ากิ่งที่จะย้ายมีรายการลงวันก่อนหรือเท่ากับเส้นกระทบยอดของสายแม่เดิมหรือสายแม่ใหม่ → ปฏิเสธ (409)
**ทางออกถ้าจำเป็น:** โยกเงินออกให้เหลือ 0 → ย้าย → โยกกลับ · เงินเดินผ่านรายการที่มองเห็นได้ ไม่ใช่เปลี่ยนเงียบ ๆ

### แสดงข้อมูลที่เก็บไว้ทันที แล้วโหลดใหม่เบื้องหลัง
`2026-09-24`

**เป้าหมาย: รองรับผู้ใช้ที่เน็ตช้าตอนเปิดให้คนอื่นใช้** ไม่ใช่ความสะดวกของเจ้าของ

```
เน็ตดี   รอ 1 วินาที   →  รำคาญนิดหน่อย
เน็ตช้า  รอ 8 วินาที   →  ปิดทิ้งแล้วไม่กลับมา
```

**ทำ**
1. เก็บคำตอบจากเซิร์ฟเวอร์ใน `localStorage` — **ห้ามเก็บเลขที่ฝั่งหน้าจอคำนวณเอง**
2. เปิดแอป → แสดงของเก่าทันที + ป้าย "ข้อมูลเมื่อ 14:32 · กำลังอัปเดต…" → โหลดใหม่เบื้องหลัง
3. `cache ≤ 3 วัน` แสดงทันที · `> 3 วัน` พยายามโหลดก่อน **ถ้าล้มเหลวให้แสดงของเก่าพร้อมป้ายเตือน ห้ามแสดงหน้าว่าง**
4. ปุ่ม sync ที่หัวหน้าแรก
5. ใส่ timeout ให้ `fetch` ฝั่งหน้าจอ (~10 วินาที) + ปุ่มลองใหม่

**เหตุผลข้อ 1 — ห้ามคำนวณยอดฝั่งหน้าจอ:** ยอดเงินไม่ได้ถูก "เขียน" แต่ถูก "คำนวณ" จาก view · ถ้า cache คำนวณเอง จะมีสูตรคำนวณเงินสองชุด (SQL + JS) แล้ววันหนึ่งจะให้คำตอบไม่ตรงกันโดยไม่มีอะไรบอก — **การมีสูตรคำนวณเงินสองชุดคือหนี้ที่จ่ายคืนแพงที่สุดในระบบบัญชี**

**เหตุผลข้อ 3 — ข้อมูลเก่าดีกว่าไม่มีข้อมูล** ตราบใดที่บอกชัดว่าเก่า · คนเน็ตช้าที่โหลดไม่สำเร็จจะเห็นหน้าว่างเปล่าทั้งที่มีข้อมูลอยู่ในเครื่อง

**เหตุผลข้อ 5:** `AbortSignal` ใส่ไว้แล้วฝั่ง Worker→LINE แต่ฝั่งมือถือ→Worker ยังไม่มี · บนเน็ตแย่ request จะค้างไปเรื่อย ๆ ผู้ใช้ไม่ได้ทั้งข้อมูลและไม่ได้ทั้ง error ซึ่งแย่กว่าทั้งสองอย่าง

**ไม่ทำ · cache version / ETag** — ลดขนาดข้อมูลแต่ไม่ลดจำนวนรอบวิ่งไปกลับ ซึ่ง**รอบคือตัวที่กินเวลาบนเน็ตช้า ไม่ใช่ขนาด** · ค่อยทำตอนรายการเดินบัญชียาวหลายร้อยแถวใน v1 พร้อมกับการแบ่งหน้า

**ไม่ทำ · offline-first** (เขียนได้ตอนไม่มีเน็ต) — ต้องมี IndexedDB + คิวรอส่ง + วิธีตัดสินเมื่อข้อมูลชนกัน · คนละขนาดกับ cache และยังไม่ใช่ปัญหาที่มี

**เหตุผลที่ backend ต้อง soft delete แม้ผู้ใช้สั่ง "ลบ":** `entry.pocket_id` อ้างถึงแถวนี้ · ลบจริงแล้ว FK พังหรือรายการกลายเป็นกำพร้า
**เหตุผลที่ทั้งสองแบบต้องยอดเป็น 0:** ถ้าเอากระเป๋าที่มีเงินออกจากสายตา เงินจะหายจากยอดรวมแต่ยังอยู่ในธนาคารจริง → กระทบยอดเจอส่วนต่างที่อธิบายไม่ได้ตลอดไป
**เหตุผลที่ห้ามมีลูก active:** ลูกจะกลายเป็นกำพร้าแล้วเลื่อนขึ้นระดับบน ดูเหมือนบัญชีแยกทั้งที่อยู่ใต้กระเป๋าที่ถูกเอาออกไปแล้ว

**เตือนชื่อซ้ำ — เตือน ไม่ใช่ห้าม**

```
ชนกับที่ใช้อยู่   "มีกระเป๋าชื่อนี้อยู่แล้ว — สร้างต่อไหม"   [ยกเลิก] [สร้าง]
ชนกับที่จัดเก็บ   "เคยมีกระเป๋าชื่อนี้ในที่จัดเก็บ"          [เอากลับมา] [สร้างใหม่]
ชนกับที่ลบแล้ว    ไม่เตือน
```

## หนี้เทคนิค

### `kind` ยังไม่มีพฤติกรรมจริง
`2026-09-23` · ยืนยันตอน PR #24

`pocket-app-design.md` §4 บอกว่า `kind` "เปลี่ยนวิธีคำนวณและแสดงผล" แต่ view ไม่ได้แยกแยะ — ตอนนี้แค่เก็บค่า

**เหตุผลที่ยังไม่ทำ:** ถ้าใส่พฤติกรรมตอนนี้คือการประดิษฐ์กฎที่เอกสารไม่ได้ระบุ
**เมื่อไรต้องกลับมาดู:** ตอนที่รู้ว่า `flow_through` ควรทำอะไรจริง ๆ — และต้องทบทวน reconcile ด้วย เพราะมันคำนวณบน rollup

### repo→repo import ต้องเป็นทิศเดียว
`2026-09-24` · เจอตอน PR reconcile

`pocket.repository` → `entry.repository` เป็นทิศเดียว ปลอดภัยอยู่

**เหตุผล:** ถ้าวันหนึ่งมีคนแก้ `assertNotReconciled` ใน `entry.repository` ให้เรียก `getPocket` จะเกิด import วน — และ ESLint ชุดปัจจุบันจับไม่ได้ เพราะห้ามแค่ข้ามชั้น ไม่ได้ห้ามวนในชั้นเดียวกัน

### membership แบบ permissive ใน rollup
`2026-09-24` · ตัดสินตอน PR #30

การไล่ลูกนับเฉพาะ node ที่ผู้ใช้เป็นสมาชิก

**เหตุผลที่รับได้ตอนนี้:** ให้ผลเดียวกับแบบเข้มงวด เพราะ recursive CTE เดินผ่านเฉพาะ node ที่เป็นสมาชิก เจอ node ที่ไม่ใช่แล้วเส้นทางขาด
**เมื่อไรต้องทบทวน:** ตอนทำกระเป๋าร่วมจริงใน v3

## บันทึกการตัดสินใจเชิงสถาปัตยกรรม (ยังไม่ทำ แต่ตัดสินแล้ว)

### `category` คืออะไร — เคาะแล้ว
`2026-09-25` · ตอบคำถามว่า category มีไว้ทำอะไร (API มีแล้วแต่ไม่มีหน้าจอ)

**นิยาม:** ป้ายบอกว่า **"ค่าใช้จ่ายรายการนี้เป็นค่าอะไร"** ผู้ใช้สร้างเองได้
**ปลายทาง:** dashboard สรุปว่าเดือนนี้ใช้จ่ายอะไรไปเท่าไร

**🔴 ต้องลบ `pocket.category_id` ทิ้ง เก็บไว้เฉพาะ `entry.category_id`**

ตอนนี้ `category_id` อยู่สองที่คนละความหมาย — บนกระเป๋า ("กระเป๋านี้ไว้ทำอะไร") และบนรายการ ("รายการนี้เป็นค่าอะไร") · สิ่งที่ต้องการคืออันหลัง

**เหตุผลที่อันบนกระเป๋าซ้ำซ้อน:** ชื่อกระเป๋าจริงของไวคือหมวดอยู่แล้ว (Mobile · Subscription · Healing · Easy pass) — ติดป้าย "ค่าโทรศัพท์" ให้กระเป๋าชื่อ "Mobile" ไม่เพิ่มข้อมูลอะไร · ส่วนการจัดกลุ่มกระเป๋าหลายใบ กระเป๋าแม่ทำหน้าที่นี้อยู่แล้ว
**เหตุผลที่ต้องลบ ไม่ใช่ปล่อยไว้เฉย ๆ:** ถ้ามีสองที่ วันหนึ่งจะมีคนสับสนว่าหมวดของรายการควรตามกระเป๋าหรือตามที่กรอก แล้วเขียนตรรกะผสมกันจนแก้ยาก

**dashboard จะมีค่าตรงไหน:** กระเป๋าที่เป็นวัตถุประสงค์เฉพาะตอบตัวเองได้จากยอดอยู่แล้ว — **ตัวที่ต้องการหมวดจริงคือกระเป๋าใช้จ่ายรวม (มือเติบ)** ที่เงินไหลออกหลายเรื่องปนกัน

**🟢 ไม่ต้องรีบ เพราะหมวดเป็นป้าย ไม่ใช่เงิน**
การแก้หมวดไม่ทำให้ยอดเปลี่ยน → **แก้ย้อนหลังได้แม้ในงวดที่ปิดแล้ว** โดยไม่ละเมิดกฎกระทบยอด (กฎนั้นคุ้มครองจำนวนเงินกับวันที่ ไม่ใช่ป้าย)
แต่ยิ่งนานยิ่งมีของค้างให้ติดป้าย และจะจำไม่ได้แล้วว่า "Shopee 871 บาท" คือซื้ออะไร

**ตัดสินตอนออกแบบ:** ห้ามบังคับใส่หมวดทุกรายการ — ถ้าบังคับ การบันทึกจะช้าลงทุกครั้งแล้วจะเลิกกรอก · **dashboard ที่มีข้อมูล 70% ดีกว่า dashboard ที่ไม่มีข้อมูลเลยเพราะคนเลิกใช้**

### D1 backup — ไม่ต้องสร้าง มีให้แล้ว
`2026-09-25` · แก้ความเข้าใจผิดที่เคยจดไว้

D1 มี **Time Travel เปิดอยู่ตลอดโดยอัตโนมัติ** ย้อนกลับได้ทุกนาทีภายใน 30 วัน ไม่มีค่าใช้จ่ายเพิ่มแม้บนแผนฟรี · ไม่ต้องตั้งค่า ไม่ต้อง export เอง

**สิ่งที่ยังควรทำคือ "ซ้อม" ไม่ใช่ "สร้าง"** — ลองกู้คืนสักครั้งตอนยังไม่มีข้อมูลสำคัญ · ตอนของหายจริงไม่ใช่เวลาที่ควรมาอ่านเอกสารครั้งแรก


### Message queue — ยังไม่ต้อง · จะจำเป็นตอน v3
`2026-09-24` · ตอบคำถามว่าคิวช่วยอะไรได้บ้าง

**ตอนนี้ไม่ช่วย** เพราะงานทุกอย่างที่มี ผู้ใช้ต้องการคำตอบทันที — เพิ่มรายการต้องเห็นยอดเปลี่ยนเดี๋ยวนั้น · เช็คยอดต้องเห็นส่วนต่างเดี๋ยวนั้น · **คิวช่วยตอนที่งานเลื่อนได้ ถ้าเลื่อนไม่ได้ก็แค่เพิ่มชิ้นส่วนให้พังโดยไม่ได้อะไร**

**จะจำเป็นตอน v3 — บอทอ่านสลิป**
```
ส่งรูปสลิป → LINE ยิง webhook → LINE รอคำตอบ
             ถ้าเราไปเรียก AI อ่านรูป (หลายวินาที) LINE จะถือว่าไม่ตอบแล้วส่งซ้ำ
             → อ่านสลิปเดียวกันสองรอบ → ลงเงินซ้ำ
ทางที่ถูก    ตอบ LINE ทันทีว่ารับแล้ว → โยนงานอ่านรูปเข้าคิว → ค่อยทำ
```
*(ยังไม่ยืนยันว่า LINE ให้เวลากี่วินาทีและส่งซ้ำกี่ครั้ง — ต้องอ่านเอกสารตอนถึงจริง)*

**v1 อาจต้อง** ถ้าแจ้งเตือนรายเดือนมีผู้ใช้หลายร้อยคน — ยิงรวดเดียวจะชนลิมิตของ LINE คิวช่วยทยอยส่งและลองใหม่

**🔴 ลำดับที่ต้องลองก่อนเสมอ: `ctx.waitUntil()`**
Cloudflare Workers ตอบผู้ใช้ไปก่อนแล้วทำงานต่อหลังส่งคำตอบได้ — ครอบคลุมเคส "งานช้า ผู้ใช้ไม่ต้องรอ" เกือบหมดโดยไม่ต้องเพิ่มโครงสร้างอะไรเลย

คิวจำเป็นเมื่อ `waitUntil` ไม่พอ:
- งานล้มแล้วต้องลองใหม่อัตโนมัติ (`waitUntil` ล้มแล้วหายเลย)
- Worker ตายกลางทางแล้วงานต้องรอด (`waitUntil` ตายตาม)
- ต้องคุมจังหวะไม่ให้ยิงถี่เกินลิมิต (`waitUntil` คุมไม่ได้)
